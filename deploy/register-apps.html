Register mesthiri's two GitHub Apps

Two Apps, so the stages that only read code cannot write it. Each button opens GitHub's App creation page with the name and permissions already filled in — you review and confirm.

Neither App has a webhook. mesthiri receives events through the workflow in your repository, not through the App, so there is nothing to deliver to. The manifests set the hook inactive and subscribe to no events — an App that listens to nothing has no inbound surface.
On "no merge permission". GitHub has no separate merge permission to withhold — merging is authorised by contents: write, which the writer App needs to push a branch at all. So the writer App could merge. mesthiri's guarantee that it never does rests on having no code path that calls the merge endpoint, and on your branch protection. Keep branch protection on: it is the control that actually enforces this.

After creating each App

  1. You land on the App's settings page. Note its App ID — it is not a secret and goes in the config file.
  2. Scroll to Private keys and click Generate a private key. A .pem downloads. GitHub will not show it again; generate a new one if you lose it.
  3. Under Install App, install it on mesthiri/sandbox only for now. An App's installation set is its blast radius: keys live in a repo's secrets, and anyone with write access to that repo can extract them.

Then wire it up

  1. In mesthiri/sandbox, edit .mesthiri/config.scm and replace the placeholder ids:
    (apps (reader READER_ID) (writer WRITER_ID))
  2. Add the two keys as repository secrets on mesthiri/sandbox: MESTHIRI_READER_KEY and MESTHIRI_WRITER_KEY, pasting the whole .pem including the BEGIN and END lines.
  3. Delete the downloaded .pem files.
  4. Verify — this is what M1's whoami exists for:
    mesthiri whoami --app reader --key reader.pem --config .mesthiri/config.scm
    It should print the installation, its permissions and the rate limit. A mismatched id and key is the likeliest mistake here, and this is what names it.
